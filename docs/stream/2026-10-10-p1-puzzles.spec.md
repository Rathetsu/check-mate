# Spec: Puzzle training (themed, non-gamified)

Date: 2026-10-10
Status: Approved (design; no code yet)
Phase: 1 · Milestone M1.5

## Goal

Deliberate tactical practice. The user picks a Lichess puzzle theme (or a
mixed set) and a difficulty, then solves puzzles on the shared board. Every
attempt is stored move by move, so Phase 4 can later explain patterns such as
"you keep missing forks". The AI layer will interpret that data; this spec
only collects it.

Decisions: 2026-10-10-12-lichess-puzzle-db-and-theme-taxonomy ·
2026-10-10-11-raw-player-data-append-only-aggregates-derived ·
2026-10-10-08-single-chessground-board-component.

## Scope

In: puzzle DB import and refresh, theme catalog, selection, solving flow,
hints, solution view, attempt storage, history page, open in analysis.
Out: Puzzle Streak, Storm, Racer, leaderboards, a competitive user puzzle
rating, daily puzzle, puzzle voting, and creating new puzzles.

## User flow

```
/puzzles → theme grid (grouped) + "Mixed" → difficulty band → puzzle
→ opponent's move auto-plays → user moves → validate
   ├ correct and the line continues → opponent's reply auto-plays → user moves …
   ├ correct and the line ends → Solved
   └ incorrect → "Not the move" → Retry (same position) | View solution
→ result card: Solved / Solved with mistakes / Failed
   → Next puzzle (same theme) · Analyze · Add to study · View source game (Lichess link)
```

## Requirements

### Data import

- **P1-PZ-01 MUST** Worker job `puzzles:import`:
  - Streams `lichess_db_puzzle.csv.zst` from database.lichess.org.
  - Upserts by `PuzzleId` and records an `ingestion_runs` row.
  - Runs monthly through a pg-boss schedule, and can be triggered manually.
- **P1-PZ-02 MUST** Each row is validated through the rules layer: the FEN
  parses, every UCI move is legal in sequence, and the final position is
  reached. Invalid rows are skipped and counted.
- **P1-PZ-03 MUST** Refreshes never delete puzzles that have attempts. A
  puzzle missing upstream is marked `retired_at` and excluded from selection.

### Theme catalog

- **P1-PZ-10 MUST** Theme keys verbatim from Lichess `PuzzleTheme.scala`,
  grouped as Lichess groups them:
  - **Motifs:** fork, pin, skewer, discoveredAttack, doubleCheck,
    hangingPiece, trappedPiece, capturingDefender, sacrifice, exposedKing,
    advancedPawn, attackingF2F7, kingsideAttack, queensideAttack.
  - **Advanced:** deflection, attraction, clearance, interference,
    intermezzo, quietMove, xRayAttack, zugzwang, defensiveMove,
    discoveredCheck, collinearMove.
  - **Mates:** mate, mateIn1 … mateIn5.
  - **Mate patterns:** backRankMate, smotheredMate, anastasiaMate,
    arabianMate, bodenMate, … (full list in the ADR source).
  - **Phases:** opening, middlegame, endgame, rookEndgame, …
  - **Special moves:** castling, enPassant, promotion, underPromotion.
  - **Goals:** equality, advantage, crushing.
  - **Lengths:** oneMove, short, long, veryLong.
  - **Origin:** master, masterVsMaster, superGM.
- **P1-PZ-11 MUST** "Mate in 4+" in the UI selects `mateIn4 OR mateIn5`.
  "Endgame tactic" maps to `endgame`. "Removing the defender" maps to
  `capturingDefender`. Labels are friendly; keys stay Lichess's.
- **P1-PZ-12 MUST** Each theme card shows its name, a one-line description
  (our own text), the count of available puzzles, and the user's solved/tried
  count.
- **P1-PZ-13 MUST** "Mixed" draws from all themes.

### Selection

- **P1-PZ-20 MUST** Difficulty bands by puzzle rating:
  - Beginner <1200
  - Easy 1200-1599
  - Intermediate 1600-1999
  - Hard 2000-2399
  - Expert ≥2400
  - Default: Intermediate, and the user's last choice is remembered.
- **P1-PZ-21 MUST** Selection picks a random puzzle:
  - in the chosen theme and band
  - not retired
  - not yet attempted by the user (falling back to the least recently
    attempted when exhausted)
  - with `popularity ≥ 0` (filters out downvoted puzzles)
- **P1-PZ-22 MUST** Selection is p95 < 100 ms on the full 6.16M-row table.
  - Suggested approach: a `rand_key` float column with a btree on
    `(rand_key)`, a GIN index on `themes`, and a seek from `rand_key >= random()`.
  - The approach is the implementer's choice, but it must be benchmarked.
- **P1-PZ-23 SHOULD** "Retry my failed puzzles in this theme" mode.

### Solving

- **P1-PZ-30 MUST** Show the puzzle FEN, animate the opponent's `Moves[0]`,
  then set the board to user-to-move. The board is oriented to the user's
  side and `movable` is restricted to that side.
- **P1-PZ-31 MUST** A user move is **correct** if it equals the expected
  solution UCI, **or** if the rules layer reports it delivers checkmate (at
  any ply). Castling written king-takes-rook is normalized. Everything else
  is incorrect (mirrors lila `moveTest.ts`, ADR 12).
- **P1-PZ-32 MUST** When the move is correct and the line continues, the
  opponent's next solution move auto-plays after 300 ms.
- **P1-PZ-33 MUST** On an incorrect move:
  - The board shows the move, then reverts after 500 ms with a "Not the
    move" message.
  - The attempt is marked as having a mistake.
  - The user may retry from the same position, or view the solution.
- **P1-PZ-34 MUST** Hint highlights the piece to move. Using it sets
  `hint_used`.
- **P1-PZ-35 MUST** "View solution" plays out the remaining line step by step
  and sets `solution_viewed`. The outcome becomes `failed`.
- **P1-PZ-36 MUST** Outcomes:
  - `solved_clean`: no mistakes, no hint, no solution viewed
  - `solved_with_mistakes`: a mistake or hint, but the user finished the line
  - `failed`: the solution was viewed
  - `abandoned`: started, never finished, closed by the next start or a
    24-hour sweep
- **P1-PZ-37 MUST** After completion:
  - **Analyze:** opens the analysis board at the puzzle position with the
    solution as the mainline and the user's wrong moves as variations,
    creating an analysis session with source `puzzle`.
  - **Add to study.**
  - **View source game:** links out to Lichess `GameUrl`.
- **P1-PZ-38 MUST** Anonymous users can solve puzzles. Attempts are stored
  only for signed-in users (verification not required,
  2026-10-11-03-soft-launch-without-email-service). A sign-in banner explains
  why history matters.

### Attempt storage

- **P1-PZ-40 MUST** An attempt row is created on the user's **first move** (not on view) and is append-only (ADR 11).
- **P1-PZ-41 MUST** One move row per user move: the expected UCI, the played
  UCI, correct or not, elapsed ms since the previous board-ready, and a
  timestamp.
- **P1-PZ-42 MUST** Each attempt snapshots the puzzle's themes, rating, FEN
  and solution at attempt time.

### History

- **P1-PZ-50 MUST** `/puzzles/history`:
  - the user's attempts, newest first, filterable by theme, outcome and date
  - per-theme summary: attempts, solved clean %, average time per solved
    puzzle
  - all computed from the raw rows at query time, with no stored aggregate
- **P1-PZ-51 MUST** No ratings, ranks or leaderboards anywhere.

## Data model

```
puzzles (id text PK,            -- Lichess PuzzleId
  fen text, moves text[],       -- UCI; moves[0] = opponent's setup move
  rating int, rating_deviation int, popularity int, nb_plays int,
  themes text[], opening_tags text[], game_url text,
  rand_key double precision, retired_at timestamptz null,
  imported_at timestamptz)
INDEX GIN (themes); INDEX (rating); INDEX (rand_key)

puzzle_attempts (id uuid PK, user_id FK CASCADE, puzzle_id FK,
  started_at, completed_at null,
  outcome text null,            -- solved_clean|solved_with_mistakes|failed|abandoned
  hint_used bool, solution_viewed bool, mistakes int,
  selection jsonb,              -- {theme|'mixed', band, mode:'normal'|'retry_failed'}
  snap_themes text[], snap_rating int, snap_fen text, snap_moves text[])
INDEX (user_id, started_at DESC); INDEX (user_id, puzzle_id)

puzzle_attempt_moves (attempt_id FK CASCADE, seq int, ply int,
  expected_uci text, played_uci text, correct bool,
  elapsed_ms int, played_at timestamptz, PRIMARY KEY (attempt_id, seq))
```

## API surface

- `GET /api/v1/puzzles/themes`: catalog with counts and the user's stats
- `GET /api/v1/puzzles/next?theme=&band=&mode=`: returns the puzzle with no
  solution beyond what the client needs
- `POST /api/v1/puzzles/:id/attempts`: returns `{attemptId}`
- `POST /api/v1/puzzle-attempts/:id/moves`: `{uci, elapsedMs}` returns
  `{correct, reply?, done, outcome?}`. The server validates using the rules
  layer, so the client is not trusted to judge correctness.
- `POST /api/v1/puzzle-attempts/:id/hint` and `/solution`
- `GET /api/v1/puzzles/history?theme=&outcome=&from=&to=`

The server is authoritative for correctness when signed in. For anonymous
play the client validates with the same `packages/chess` logic.

## Chess-authority notes

Correctness is decided by solution comparison plus the rules layer's
checkmate detection, never by heuristics. Puzzle ratings and themes are
Lichess data, shown as such.

## Phase 4 hooks

`puzzle_attempts` + `puzzle_attempt_moves` + theme snapshots give the AI
service per-motif accuracy, time-to-solve, and the exact wrong moves, through
`/api/v1/puzzles/history` (raw rows available to service auth later).

## Acceptance criteria

- The import job loads the full CSV. A re-run is idempotent (row count
  stable; `ingestion_runs` records skipped rows).
- Playwright, theme "fork" / Intermediate:
  - solving correctly → `solved_clean`
  - a wrong move then retry → `solved_with_mistakes`, with one incorrect move
    row
  - view solution → `failed`
- A mate-in-2 puzzle solved with an alternative mating move counts as correct.
- The history page shows the attempts above with the correct per-theme
  numbers.
- Selection benchmark on the full table: p95 < 100 ms across 1,000 random
  theme+band draws.
- No UI element shows a user puzzle rating.
