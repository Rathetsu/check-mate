# Spec: Studies

Date: 2026-10-10 · rewritten 2026-10-11 for M1.4
Status: Approved. Built in M1.4 (2026-10-11): 4.1 single-user, 4.2
sharing, 4.3 collaboration. See Build notes
Phase: 1 · Milestone M1.4

## Goal

Studies at Lichess parity, minus chat. A study holds up to 64 chapters. Each
chapter is an analysis tree with variations, comments, glyphs and arrows. A
study can be private, unlisted or public, cloned, liked, tagged with topics
and embedded, and edited live by invited members.

Decisions: 2026-10-10-13-study-chapters-stored-as-pgn (PGN stays the stored
format) · 2026-10-11-04-shared-collaborative-studies-ops-over-pgn (edits are
server-applied tree ops; one `studyAccess` gate) ·
2026-10-10-11-raw-player-data-append-only-aggregates-derived.

## Scope

In:
- **Single-user tools (4.1):** study and chapter CRUD; chapters from blank,
  FEN, PGN (one chapter per game) and a Lichess game URL; chapter name,
  orientation, description and mode; editing with the analysis board;
  PGN tag editor; clear annotations or variations; reorder; copy a chapter
  to another study; chapter search; next chapter; multiboard; export as PGN,
  PNG (position) and GIF (mainline); study, chapter and position links;
  chapter modes "hide next moves", "interactive lesson" and "practice with
  computer"; "Save to study" from analysis and "Save as study chapter" from
  the editor.
- **Sharing (4.2):** visibility, per-study settings, clone, likes, topics,
  browse and search public studies, embed.
- **Collaboration (4.3):** members (contributor or viewer) invited by
  username, who accept or decline; live edits over SSE; position sync;
  comment authors; presence.

Out: chat, stored server-side computer analysis (Phase 4), broadcasts,
flair. "From puzzle" chapters arrive with M1.5, explorer positions in P2,
library games in P3, all through the same chapter-creation call.

## Roles and access

`studyAccess(userId | null, studyId)` in `packages/core` is the only gate.
It returns:

| Role | Who | Can |
|---|---|---|
| `owner` | the study's `user_id` | everything, including settings, visibility, members and delete |
| `contributor` | an active member with that role | edit chapters (ops, add, rename, reorder, delete, replace), set the sync position |
| `viewer` | an active member with that role | read, even when the study is private |
| `reader` | anyone, signed in or not, when the study is public or unlisted | read |
| `none` | everyone else, and invited members who haven't accepted | nothing: every route answers **404**, never 401 or 403 |

- Every chapter query is scoped by both ids (`id = chapterId AND study_id =
  studyId`), so a chapter id from another study is a 404.
- `settings.computer = false` hides the engine panel for non-owners. It
  can't stop a browser running its own engine, as on Lichess.
- `settings.cloneable` and `settings.shareable` (`everyone`, `contributors`,
  `nobody`) control clone and export for non-owners.

## Requirements

### Studies and chapters (4.1)

- **P1-ST-01 MUST** Create (name; a blank chapter 1 is made with it),
  rename, describe and delete studies. Delete needs confirmation and removes
  every chapter.
- **P1-ST-02 MUST** Add chapters through one service call,
  `createChapters(userId, studyId, source)`, for every source:
  - blank (the starting position)
  - FEN (validated; the editor's "Save as study chapter" uses it)
  - PGN, pasted or a file: one chapter per game, named from the headers,
    up to the 64-chapter cap; a bad game is reported with its line and the
    rest are still offered
  - a Lichess game URL (`lichess.org/<8-char id>`, optionally with a color
    or ply suffix): our server fetches `lichess.org/game/export/<id>` once,
    when the user asks, with a 5 s timeout. A 429 or a missing game gives a
    plain message. It is the only runtime call to Lichess in Phase 1
  - later: puzzle (M1.5), explorer position (P2), library game (P3)
- **P1-ST-03 MUST** Chapter fields: name (1-100 characters), orientation,
  description (up to 2,000 characters), mode, PGN (the whole tree), order,
  version.
- **P1-ST-04 MUST** Editing reuses `AnalysisBoard`. Each change is a tree op
  posted to the server, applied on screen at once, and confirmed or
  rejected. The ops are those of `packages/chess/src/ops.ts`: add move,
  delete from here, promote, comment, glyphs, shapes, plus `setTags`,
  `setGamebook`, `clearAnnotations` and `clearVariations`.
- **P1-ST-05 MUST** Nothing is lost silently:
  - A "Saved" indicator shows while ops are pending and when they're done.
  - Leaving with ops pending asks first (`beforeunload`).
  - A rejected op (the move was deleted meanwhile, a limit was hit)
    reloads the chapter and says why.
  - Ops are idempotent, so two people adding the same move, glyph set or
    comment converge. Only "replace chapter" checks a version and can
    answer 409.
- **P1-ST-06 MUST** The server validates everything through
  `packages/chess`: imported PGN, replaced chapters and every op. Errors use
  the PGN/FEN error envelope (code, message, line, ply).
- **P1-ST-07 MUST** Reorder chapters: drag on desktop, up/down buttons on
  phones.
- **P1-ST-08 MUST** Export:
  - chapter `.pgn` with `[Event "<study>: <chapter>"]`, `[StudyName]` and
    `[ChapterName]`, and the whole study as one multi-game `.pgn`
  - CheckMate data (`[%cm-…]`: lesson hints, comment authors) only when
    "CheckMate extensions" is chosen; authors are then written as usernames,
    or "Deleted user"
  - PNG of the current position and GIF of the mainline, drawn in the
    browser with the user's piece set and board colors
  - study, chapter and position links
- **P1-ST-09 MUST** Limits: 64 chapters per study, 500 KB of PGN and 20,000
  moves per chapter, 200 owned studies per user. A limit gives a clear error,
  never a truncation.
- **P1-ST-10 MUST** The study list shows name, chapter count, owner, likes,
  updated time and a thumbnail of chapter 1, drawn without chessground.
- **P1-ST-12 MUST** Copy a chapter to another study the user can edit,
  within that study's 64-chapter cap. (Clone is P1-ST-20.)
- **P1-ST-13 MUST** The study remembers the last chapter and move
  (`studies.position`); opening `/studies/<id>` lands there.
- **P1-ST-14 MUST** Chapter panel: search by name, rename, reorder, delete,
  copy to study, "Next chapter".
- **P1-ST-15 MUST** PGN tag editor for the chapter's headers. `FEN`, `SetUp`
  and `Variant` can't be changed there (they'd move every path); make a new
  chapter instead.
- **P1-ST-16 MUST** Clear annotations (comments, glyphs, arrows) or clear
  variations (keep only the mainline) for a chapter, after confirmation.
- **P1-ST-17 MUST** Multiboard: every chapter's current position as a small
  board, paginated, each linking to its chapter.
- **P1-ST-18 MUST** Chapter modes (Lichess parity):
  - **Normal.**
  - **Hide next moves:** readers see the move list only up to the furthest
    move they've reached.
  - **Interactive lesson** (gamebook): editors write, per move, the comment
    shown after it, a hint, and the text shown when the student plays
    something else. Students play the side the chapter is oriented to: the
    mainline is right, a variation shows its comment and sends them back,
    and a move off the tree shows the deviation text. Ported from lila
    `gamebookPlayCtrl`.
  - **Practice with computer:** the student plays from the chapter's
    position; each move is judged with the engine before and after it (lila
    `practiceCtrl` thresholds on winning chances) and the engine replies.
    Practice moves stay in the student's browser.
  - Editors can switch between editing and previewing a lesson or practice
    chapter.
- **P1-ST-19 MUST** Elsewhere: the analysis board's "Save to study" (a new
  chapter in a chosen study, or overwrite a chosen chapter after
  confirmation), the editor's "Save as study chapter", and the share
  dialog's "Save as study and share" when a link would be too long.

### Sharing (4.2)

- **P1-ST-11 MUST** Visibility: private (default), unlisted (anyone with
  the link) or public (also listed). Settings: computer analysis, cloneable,
  shareable/exportable, sticky sync. Owner only.
- **P1-ST-20 MUST** Clone: a private copy owned by the user, with every
  chapter, when the study allows it; counts toward the 200-study cap.
- **P1-ST-21 MUST** Likes (one per user per study) and topics (up to 10,
  1-40 characters each).
- **P1-ST-22 MUST** `/studies` tabs: mine, member of (plus pending invites),
  liked, public. Sorts: hot, newest, recently updated, most liked, name.
  "Hot" is lila's study rank: the creation time pushed forward by
  `min(int(5·ln(likes) + 1), likes)` days. Search by name; `/studies/topic/<topic>`.
- **P1-ST-23 MUST** Signed-out visitors can read public and unlisted studies
  (read-only board, engine allowed by the setting).
- **P1-ST-24 MUST** Embed: `/embed/study/<id>/<chapterId>` shows a public or
  unlisted chapter with no site chrome and no engine, and may be framed by
  any site. Every other page refuses framing (`frame-ancestors 'self'`).

### Collaboration (4.3)

- **P1-ST-30 MUST** The owner invites members by username as contributor
  or viewer (up to 30). An invite gives no access until the invitee accepts
  it from "Member of"; they can also decline. The owner can change a role or
  remove a member; a member can leave.
- **P1-ST-31 MUST** Everyone viewing a study sees edits live: ops,
  chapter changes and settings changes arrive over one SSE stream per study
  per tab. Losing the stream reconnects and catches up; a lost op means the
  chapter is reloaded, never shown wrong.
- **P1-ST-32 MUST** Sync: with sync on, members follow the position a
  contributor navigates to; newcomers land there.
- **P1-ST-33 MUST** Comments are one per author per move and show the
  author's username. A deleted account's comments stay, shown as "Deleted
  user". Authors are stored by account id, so someone who later takes the
  freed username can't pose as the author. Pasted PGN can't set an author.
- **P1-ST-34 MUST** Presence: members see which members are viewing, and a
  count of signed-out readers.
- **P1-ST-35 MUST** Any change to visibility, membership or a role takes
  effect on open streams at once (they reconnect and re-check access).

## Data model

Chapters are owned by their study and have no `user_id` (a departure from
CORE-50's wording): every read goes through `studyAccess`, and the owner is
on `studies`. **Deleting an account deletes its studies, including what
members added to them.** Comments by a deleted member stay in other people's
studies, shown as "Deleted user".

```
studies (id uuid PK, user_id → user CASCADE,   -- owner
  name text, description text,
  visibility text DEFAULT 'private',           -- private | unlisted | public
  settings jsonb,                              -- {computer, cloneable, shareable, sticky}
  topics text[] DEFAULT '{}',                  -- GIN index
  position jsonb,                              -- {chapterId, path}: remembered/sync position
  created_at, updated_at)
  INDEX gin (name gin_trgm_ops)                -- search (4.2)
study_chapters (id uuid PK, study_id → studies CASCADE,
  ord int, name text, orientation text, description text,
  mode text DEFAULT 'normal',                  -- normal | conceal | gamebook | practice
  pgn text,                                    -- the whole tree, CheckMate extensions included
  initial_fen text, source_type text, source_id text,
  version int DEFAULT 1, created_at, updated_at,
  UNIQUE (study_id, ord) DEFERRABLE INITIALLY DEFERRED)
study_likes (study_id → studies CASCADE, user_id → user CASCADE,
  created_at, PK (study_id, user_id))          -- 4.2; counts are computed on read
study_members (study_id → studies CASCADE, user_id → user CASCADE,
  role text, status text,                      -- contributor | viewer; invited | active
  created_at, PK (study_id, user_id))          -- 4.3
```

What standard PGN can't hold is kept in comment commands, stripped from
plain exports: `[%cm-by <userId>]` (comment author), `[%cm-hint …]` and
`[%cm-deviation …]` (lesson text).

## API surface

JSON bodies; errors use the CORE-41 envelope. Every route answers 404 when
`studyAccess` gives `none` or too low a role for a write the caller could
not see anyway; a reader trying to write gets 403.

- `GET /api/v1/studies?tab=mine|member|invites|liked|public&q=&topic=&sort=hot|newest|updated|liked|name&page=`
- `POST /api/v1/studies` `{name}` → `201 {id, chapterId}`
- `GET /api/v1/studies/:id` → study, role, chapter list (id, name, ord,
  orientation, mode, initialFen, version), members for the owner
- `PATCH /api/v1/studies/:id` `{name?, description?, visibility?, settings?, topics?}` (owner)
- `DELETE /api/v1/studies/:id` (owner)
- `POST /api/v1/studies/:id/clone` → `201 {id}`
- `PUT /api/v1/studies/:id/like` `{liked}` → `{likes, liked}`
- `PUT /api/v1/studies/:id/position` `{chapterId, path}` (contributor)
- `POST /api/v1/studies/:id/reorder` `{chapterIds}` (contributor)
- `POST /api/v1/studies/:id/chapters` `{source: {type: 'blank'|'fen'|'pgn'|'lichess', fen?, pgn?, url?}, name?, orientation?, mode?}` → `201 {ids}`; a bad PGN game gives `400` with its error
- `GET /api/v1/studies/:id/chapters/:chapterId` → chapter with PGN and version
- `PATCH /api/v1/studies/:id/chapters/:chapterId` `{name?, orientation?, description?, mode?}`
- `PUT /api/v1/studies/:id/chapters/:chapterId` `{pgn, version}` → `{version}`, or `409` when the version moved on
- `DELETE /api/v1/studies/:id/chapters/:chapterId`
- `POST /api/v1/studies/:id/chapters/:chapterId/ops` `{op, clientId}` → `{version}`; `400 ILLEGAL_MOVE` (with ply), `409 NODE_GONE`, `413 TOO_LARGE`
- `POST /api/v1/studies/:id/chapters/:chapterId/copy` `{toStudyId}` → `201 {id}`
- `GET /api/v1/studies/:id/export.pgn?extensions=1`, `GET /api/v1/studies/:id/chapters/:chapterId/export.pgn?extensions=1`
- `GET /api/v1/studies/:id/events` (SSE): `hello`, `op`, `reset`, `meta`, `position`, `presence`
- Members (4.3): `POST /api/v1/studies/:id/members` `{username, role}` (owner),
  `PATCH|DELETE /api/v1/studies/:id/members/:userId` (owner; DELETE also by
  the member to leave), `PUT /api/v1/studies/:id/membership` `{accept}` (the
  invitee)

## Chess-authority notes

The server validates chapter content and every op through the rules layer.
Study text (comments, lesson text) is user-authored and never treated as
chess truth. Practice verdicts come from the engine with provenance, in the
student's browser, and are never stored.

## Phase 4 hooks

`/api/v1/studies/*` lets the AI service read what openings and positions a
user studies. `source_type`/`source_id` link chapters back to games and
puzzles.

## Acceptance criteria

4.1
- Playwright: create a study → add blank, FEN and a 2-game PGN (4 chapters)
  → annotate → reload → everything persists.
- Playwright: export the study → import it as a new study → identical
  chapters.
- Playwright: each chapter mode (hide next moves, a lesson with a wrong and a
  right move, practice with the fake engine).
- Playwright: a chapter from a Lichess game URL (Lichess stubbed).
- Playwright: PNG and GIF downloads exist and aren't empty.
- Vitest: an op round-trips through storage; `[%cm-*]` survives storage and
  is stripped on plain export; an illegal move gives `400 ILLEGAL_MOVE` with
  its ply; the 65th chapter and the copy cap are refused; a forged
  `[%cm-by]` in imported PGN is stripped; `setTags` on `FEN` is refused; a
  chapter id from another study is a 404; cross-user access is a 404.

4.2
- Vitest: the visibility × role matrix; the clone setting; like counts after
  a liker deletes their account.
- Vitest: A and B are members of and like each other's studies → delete A →
  B's study survives, A's studies are gone.
- Playwright: publish → open signed out; embed headers; browse, search and
  topic pages.

4.3
- Vitest: concurrent ops serialize with no lost update and publish in
  version order; `setNags` from two users converges; a viewer can't apply
  ops; an invited but not accepted user has no access; a removed member
  gets a 404; a deleted author's comment shows "Deleted user".
- Playwright, two browsers: invite → accept → live edits both ways → sync →
  the viewer is read-only; a forced stream close reconnects and catches up.
- Manual: two browsers through Caddy at `https://localhost`.

## Build notes

### M1.4 (2026-10-11)

- **Ops are fast enough without a cache.** One op on a ~480 KB stored
  chapter (12,000 moves) costs about 110 ms end to end: parse, apply, write,
  save. No lazy `fen` and no parse cache were needed.
- **`ord` is a sort key, not unique.** Drizzle 0.45 can't declare a
  deferrable unique; ties (two chapters added at the same moment) fall back
  to creation time. Reorder rewrites every chapter's `ord`.
- **`preview_fen`** (the end of the mainline) was added to chapters for the
  list thumbnails and the multiboard, so listing never parses PGN.
- **A study's first chapter can be given** (`POST /api/v1/studies` takes an
  optional `chapter`), which "Save to study" uses for a new study.
- **A multi-game PGN with a bad game is refused** with that game's number,
  line and message, rather than importing the rest silently. The import
  dialog on the analysis board still lets the user pick the good games.
- **Chapter from a Lichess URL** is tested in Vitest against a stub server
  (`LICHESS_URL`): the fetch is server-side, which a browser test can't
  intercept.
- **Comment authors on screen** come from the chapter's stored authors, the
  study's members, the owner and the viewer, so a new comment shows its
  author before any reload. An id with no name yet shows no name; a deleted
  account shows "Deleted user".
- **Positions:** a contributor with sync on shares their position (300 ms
  after moving), which is also where the study opens next time. With sync
  off nothing is shared or remembered. Following someone else's position is
  never sent back, so two synced contributors don't echo each other.
- **Live updates** keep, per tab, the chapter version the screen shows:
  a remote op applies only if it is the next version; anything else, or a
  remote change while the tab's own ops are on the way, reloads the chapter
  once they settle. Each `hello` (first connect and every reconnect) checks
  versions, and a reconnect also reloads the study (roles may have changed).
- **Embed** reads as a signed-out visitor, so the owner's private studies
  never embed, and it shows a Source link (AGPL §13) since there's no site
  footer.
- **Framing:** every page except `/embed/*` now sends
  `Content-Security-Policy: frame-ancestors 'self'`.
- **Tests:** Vitest covers every 4.1-4.3 criterion above (studies,
  study-sharing, study-members test files). Playwright: the spec flow,
  export and re-import, PNG/GIF/PGN downloads, an interactive lesson,
  practice with the fake engine, hide next moves, Save to study, publish and
  read signed out, embed headers, browse/search/topic/like/clone, and a
  two-browser run (invite, accept, live edits both ways, sync, demotion to
  viewer, catching up after the forced reconnect).
