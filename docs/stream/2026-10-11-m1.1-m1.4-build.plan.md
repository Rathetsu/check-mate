(docs/stream/2026-10-11-phase-1-implementation.plan.md) sketches M1.1-M1.4 in

## Library facts that shape the design (verified 2026-10-11)

chessops 0.15.1 (read from its source):
- **No line or column anywhere.** Games split **only on blank lines.** An
  unclosed `{` swallows every game after it, and a missing blank line
  between games makes the next game's tags parse as movetext. → `pgn.ts`
  splits the file into games itself, by header blocks, and records each
  game's start line. chessops then parses one game at a time.
- **Ambiguous and illegal SAN both come back `undefined`.** → On failure,
  count the legal moves that match the SAN's piece and destination: two or
  more is `AMBIGUOUS_MOVE`, otherwise `ILLEGAL_MOVE`.
- **`startingPosition` maps `Chess960` to standard chess.** → `pgn.ts` checks
  `[Variant]` itself, plus X-FEN castling, for `UNSUPPORTED_VARIANT`.
- **`Chess.fromSetup` returns only the first error,** and silently drops bad
  castling rights and en passant squares. → `validateSetup` runs each check
  separately, and compares the requested castling and en passant fields with
  the normalized ones to report "bad castling" and "invalid en passant".
- Unknown comment commands (`[%cm-hint …]`) survive in the comment text.
  `;` comments and position glyphs written as text (`+-`, `=`) are dropped.
  `makePgn` writes every NAG as `$n`.
- `parseFen` already splits on `_` (URL FENs) and accepts 1-6 fields.
- `toSetup()` uses `legalEpSquare`, so `makeFen(pos.toSetup(), {epd:true})`
  is already the normalized `positionKey`.
- `compat.scalachessCharPair(move)` is lila's 2-character node id. Moves are
  normalized with `normalizeMove` first, so e1g1 and e1h1 give the same id.
- chessops moves castle king→rook (e1h1). `node.uci` stores standard UCI
  (e1g1) for the engine and export, and one helper in `moves.ts` converts.
- `outcome()` doesn't cover threefold or fifty-move. `gameStatus` adds both,
  from the path's position keys and `halfmoves`.

chessground 10.4.2 (GPL-3.0-or-later, no runtime deps):
- **It observes its own resizes,** so the wrapper only gives the mount
  `aspect-ratio: 1` and a width. P1-BD-07 needs no code of ours.
- **`set({fen})` resets user shapes,** and `set()` replaces `dests` and
  `autoShapes` instead of merging. → `Board` always passes `fen` with
  `drawable.shapes`.
- **No promotion UI.** → Port lila's `ui/lib/src/game/promotion.ts` pattern:
  detect the move in `movable.events.after`, draw an overlay inside
  `.cg-wrap`, then `setPieces` on pick or `set({fen})` on cancel.
- **The brushes already follow the Lichess modifier keys:**
  - plain right-drag: green
  - shift/ctrl + right-drag: red
  - alt/meta: blue
  - both: yellow

  Spare pieces use `dragNewPiece(piece, event)`. Free mode uses
  `movable.free` with `draggable.deleteOnDropOff`.

stockfish 19.0.1 (GPL-3.0):
- **Builds:**
  - lite: `bin/stockfish-19-lite-single.{js,wasm}` (1.9 MB) and
    `stockfish-19-lite.{js,wasm}` (multi-threaded)
  - full: `stockfish-19-single.{js,wasm}` and `stockfish-19.{js,wasm}`,
    99 MB each
- **The NNUE is inside the wasm,** and the wasm must sit next to its `.js`.
- **The worker also posts `{percent, loaded, total}` objects.** The parser
  skips non-strings, and the Full download progress bar reads them.
- **Engine names:**
  - lite single-threaded: `id name Stockfish 19 Lite WASM` (seen in the
    binary)
  - the other builds, inferred from `build.js`: "… Multithreaded" when
    threaded

Late research (2026-10-11), corrections to the sections below:
- **lila-tablebase:**
  - Endpoint `GET /standard?fen=`.
  - Flags: `--standard <dir>` (repeatable). `--bind` defaults to
    `127.0.0.1:9000`, so the container passes `0.0.0.0:9000`.
  - Its Dockerfile sets `USER lichess` without creating that user, so ours
    creates it. Build needs Rust ≥ 1.85 (edition 2024) plus `libclang-dev`.
  - A missing table answers 200 with `category: "unknown"` and `dtz: null`.
    `probeTablebase` treats `unknown` as not covered.
  - Probing needs both the WDL and DTZ files, plus the tables reachable by
    captures.
- **Tablebase files:**
  - 3-5 pieces = 290 files, about 938 MiB.
  - `fetch-tablebases.sh` uses a non-Lichess mirror that publishes an md5
    checksum file. The URL is pinned in the script.
- **Glyphs:**
  - They live in scalachess `Glyph.scala`, not lila.
  - Only move (7 `□`) and zugzwang (22 `⨀`) are in the **move** group there.
    The UI follows scalachess's grouping, and P1-AN-04 is reworded at the
    M1.2 gate.
  - Observation: 146 N, 32 ↑↑, 36 ↑, 40 →, 132 ⇆, 138 ⊕, 44 =∞, 140 ∆.
- **Hot sort:** lila `Study.Rank.compute` = `createdAt + min(int(5·ln(likes)
  + 1), likes) × 24 h` (0 for no likes).
- **Advice** (lila `modules/tree/src/main/Advice.scala` and scalachess
  `eval.scala`):
  - win chances `2/(1+e^(−0.00368208·cp)) − 1`, cp clamped to ±1000
  - mate maps to `cp = (21 − min(10, |n|)) × 100`
  - a drop ≥ .1 / .2 / .3 is an inaccuracy / mistake / blunder
  - MateCreated: inaccuracy if the previous cp < −999, mistake if < −700,
    else blunder. MateLost mirrors it (> 999, > 700).
- **Practice mode** (lila `practiceCtrl.ts`):
  - `shift = −povDiff`, which is on half that scale
  - `< 0.025` good, `< 0.06` inaccuracy, `< 0.14` mistake, else blunder
  - the engine's best move is always good
- **npm:** `gifenc` 1.0.3 (MIT, ships no types, so one local `.d.ts`);
  `cmdk` 1.1.1 (MIT).
- **Lichess limits, for reference:** 64 chapters, 3,000 nodes per chapter,
  100 KB PGN import. The spec's 20k nodes and 500 KB stay.

Next 16 (from `apps/web/node_modules/next/dist/docs`): route handlers get
params as `ctx.params` (a Promise, typed by the global `RouteContext<'/x/[id]'>`).
Turbopack bundles `new Worker(new URL('./x.worker.ts', import.meta.url))`.

## M1.1 Board + rules + PGN/FEN

### 1. `packages/chess` (new workspace package `@checkmate/chess`)
- `package.json`: `exports: { ".": "./src/index.ts" }`, dependency `chessops`
  pinned `0.15.1` (register row exists). `tsconfig.json`: `lib: ["ES2023"]`,
  `types: []` (CORE-02). A `test/no-dom.test.ts` isn't needed: `tsc` fails
  on any DOM or Node global.
- `fen.ts`: `parseFen(text) → Result<Position, FenError>` (trims first),
  `makeFen`, `validateSetup(fen) → {ok:true, pos} | {ok:false, reasons[]}`
  with every P1-PG-10 reason (see facts above), `fenToUrl`/`fenFromUrl`
  (`_` ↔ space; chessops already accepts `_`).
- `moves.ts`: `legalDests` (= `chessgroundDests`), `applyUci`, `applySan`
  (with the ambiguous/illegal split), `toSan`, `toStandardUci`,
  `gameStatus(pos, pathKeys)`.
- `keys.ts`: `positionKey(pos)` = `makeFen(pos.toSetup(), {epd:true})`.
  `gameFingerprint` and `terminalKey` wait for P2/P3 (CORE-11 lists them,
  but nothing calls them before then).
- `pgn.ts`:
  - `splitGames(text)` → `{index, line, offset, text}[]`: strips BOM,
    normalizes CRLF, starts a new game at a tag line that follows movetext,
    and removes blank lines inside movetext so chessops doesn't split there.
  - `indexPgn(text) → {games: {index, headers, line, status, error?}[]}`:
    parses and validates one game at a time and keeps only headers. Caps:
    10 MB and 5,000 games (`TOO_LARGE`).
  - `loadGame(text, index) → Result<TreeCursor, PgnError>`.
  - `PgnError {gameIndex, line, column, ply?, san?, code, message}`. For a
    move error, a small tokenizer walks the game text in PGN order (mainline
    move, then its sibling variations, then onward) to find the n-th SAN
    token's line and column. It skips comments, NAGs and move numbers, and
    has no chess logic.
  - Comment commands: `[%cal]/[%csl]` → shapes, `[%clk]` → clock,
    `[%eval]` → `importedEval {score, depth?, source:'imported'}`
    (P1-PG-40), `[%cm-*]` → `node.ext`.
  - `makePgn(cursor, {variations, comments, clocks, extensions})`
    (P1-PG-23). `extensions` writes `[%cm-*]` (off by default).
- `tree.ts`: `TreeCursor` per P1-BD-20..24. Node `{id, ply, uci, san, fen,
  positionKey, comments[], nags[], shapes[], clock?, importedEval?, ext?,
  children[]}`. A 20,000-node cap gives `TOO_LARGE` (P1-PG-31). Mutations
  bump a `version` number so React can subscribe.
  - **Paths stay stable across every re-parse,** because studies address
    nodes by path:
    - Each id is `scalachessCharPair(normalizeMove(pos, move))`, the same
      for `O-O`, e1g1 and e1h1.
    - Identical sibling variations are merged on import.
    - Null moves (`--`) are rejected on import.
    - Paths are `encodeURIComponent`-ed in links, because the id alphabet
      includes `#%&?/`.
  - Property test: `parse(make(tree))` equals `tree` across the corpus,
    ids included.
  - **Cost benchmark** (Vitest): parse + `makePgn` on a 500 KB / 20k-node
    fixture, with a ~100 ms budget. M1.4 runs one parse and one write per
    op, so this matters there. Over budget → compute `fen` and
    `positionKey` lazily.
- `analysis.ts`: the CORE-20 `AnalysisProvider` interface and its types, plus
  `createFakeProvider()` (CORE-23), which returns deterministic lines from the
  rules layer (for example, the first legal moves with fixed scores).
  `validateVariation` checks legality first, for every provider.
- `fixtures/` + `README.md`:
  - an authored study export (synthetic, Lichess format)
  - one Lichess game export (CC0, fetched once and committed)
  - one Lichess broadcast round (CC BY-SA, attributed)
  - a synthetic Chess.com archive
  - the malformed set
  - The register row already exists.

### 2. Engine
- `scripts/copy-stockfish.ts`, run by `apps/web` `postinstall`, copies the
  four `bin/stockfish-19*.{js,wasm}` builds into `public/engine/` (already
  gitignored). The Dockerfile copies `scripts/` before `pnpm install`.
  The two full builds add about 200 MB to the web image. That's accepted:
  Full is opt-in, and serving it from our own origin keeps COEP simple.
- Release checklist item 7: `/about` links the stockfish.js v19.0.1 source
  for the WASM we serve.
- `apps/web/src/engine/browser-stockfish.ts` (the only UCI parser, CORE-22):
  - It implements `AnalysisProvider` over a `Worker`.
  - Each search gets an id. A new search sends `stop` and waits for
    `bestmove` before `position`/`go`, and output from an old id is
    dropped (P1-AN-16, the lila ceval pattern).
  - MultiPV 1-5, depth 16-40 or infinite, hash 16-256 MB.
  - Threads: `hardwareConcurrency − 1`, max 8, only when
    `crossOriginIsolated`; otherwise the single-threaded build.
  - Provenance comes from the `id name` line.
  - On `visibilitychange` to hidden it stops. A failed load gives an error
    state, and the board keeps working (P1-AN-17).
- `engine/index.ts`: `getProvider()` returns the fake provider only when
  `NEXT_PUBLIC_E2E=1` and `?engine=fake`.
- UI:
  - `engine-panel.tsx`: lines show score, depth and SAN PV truncated with

  - `eval-bar.tsx`: white/gray/black only (P1-UI-14).
  - `engine-settings.tsx`: flavor choice, with a size warning and a

  - The best-move arrow goes in `autoShapes`.
  - The provenance label (P1-AN-15).
- `next.config.ts` `headers()`: COOP `same-origin` + COEP `require-corp` on
  `/analysis/:path*` and `/studies/:path*` only. The embed route stays out.

### 3. Tablebase (decision 15)
- `services/tablebase/Dockerfile`: a multi-stage Rust build of upstream
  lila-tablebase at a pinned commit, unmodified, running on a slim runtime
  image.
- Compose service `tablebase`:
  - profile `tablebase`, so the stack runs without it
  - not public: Caddy never routes to it, and its port is published only on
    `127.0.0.1:9000` for `pnpm dev`, like postgres
  - `${TABLEBASE_DIR:-./data/tablebase}:/tablebase:ro` (`data/` gitignored)
- `scripts/fetch-tablebases.sh [345|ci]`: downloads the 3-5 piece tables
  from a non-Lichess mirror into `data/tablebase` and verifies checksums.
  `ci` is only KRvK and KQvK.
- `packages/core/src/services/tablebase.ts`:
  - `probeTablebase(fen)` validates through `packages/chess` and requires no
    castling rights and a piece count ≤ `TABLEBASE_MAX_PIECES` (default 5).
  - It returns `null` when `TABLEBASE_URL` is unset, on a 1.5 s timeout, or
    on any error (P1-AN-52).
  - Otherwise it returns `{label: 'Tablebase', category, dtz, moves[]}`.
- `GET /api/v1/tablebase?fen=` (`publicRoute`): 200 with the result, or 204
  when the position isn't covered or the service is unavailable.
- `components/analysis/tablebase-panel.tsx`: hidden on `null`. Clicking a
  move plays it as `addNode`. It never touches the engine panel or eval
  bar.
- CI builds the image with GitHub Actions layer caching and runs it with the
  `ci` table set.
- `data/` goes in `.gitignore` and `.dockerignore`. `.env.example` gains
  `TABLEBASE_URL` (dev: `http://127.0.0.1:9000`) and `TABLEBASE_MAX_PIECES=5`.
- **Naming and licence (user decision, 2026-10-11):** the table files are free
  to use. There is no licence gate and no register row for them. New code,
  UI, scripts, env vars and docs call them "tablebase" only.
  - The UI label is "Tablebase", which still keeps provenance clear: never
    the engine panel or eval bar.
  - At the M1.2 doc gate, the analysis spec (P1-AN-50..52), `architecture.md`,
    `status.md` and the roadmap risk row are reworded to match.
  - The accepted ADR 2026-10-11-06 is left as written (ADRs are
    append-only).
  - lila-tablebase, the code we run, still gets its register row, since
    it's an AGPL component.

### Access: `packages/core/src/services/study-access.ts`
- `studyAccess(userId | null, studyId)` returns one of:
  - `owner`
  - `contributor` (active)
  - `viewer` (active)
  - `reader` (public or unlisted)
  - `none`, which every caller turns into a 404 (CORE-51/52)
  - An `invited` member is not a member yet.
- **Every chapter query is `WHERE id = $chapterId AND study_id = $studyId`:**
  ops, GET, PUT, export, copy, and the position write. Without that, a
  contributor of study X could edit study Y's chapters by id. One test
  proves it: a contributor of X posts an op to Y's chapter → 404.
- Ops and chapters: owner or contributor.
- Settings, visibility, members and delete: owner only.
- Clone and export check `settings.cloneable` / `settings.shareable`
  against the role.
- The `computer` setting only hides the engine UI, since the engine runs in
  the user's browser anyway (Lichess does the same).

### 4.3 Collaboration
- Members (`study_members`), with a cap of 30 per study:
  - The owner invites by username.
  - The invitee accepts or declines from the "Member of" tab, which lists
    only `active` memberships, plus a pending-invites list.
  - The owner can change a role or kick; a member can leave.
  - A comment's author is stored as `[%cm-by <userId>]` and resolved to a
    username when shown or exported. A deleted account shows as "Deleted
    user", which also stops anyone who later takes the freed username from
    looking like the author.
  - No other column references `user`. An `invited_by` column would escape
    the FK cascade test and could block `deleteUser`.
- `GET /api/v1/studies/:id/events` (SSE, `publicRoute`, reader or above):
  - It sends `hello {chapterId: version}` first (one `SELECT id, version`).
    This covers both the fetch/subscribe race and EventSource reconnects,
    so there's no `Last-Event-ID`.
  - Events:
    - `op` {chapterId, version, op, by, clientId}
    - `reset` {chapterId} for a replace-chapter `PUT` and the
      clear-annotations/variations ops: refetch that chapter
    - `meta`, which means refetch the study: chapters added, removed,
      renamed or reordered, plus settings and role changes
    - `position`
    - `presence`
  - Any visibility, member or role change closes every stream for that
    study. The reconnect, plus `hello`, re-checks access, and a 404 stops
    EventSource from retrying. There is no per-connection re-check.
  - Headers: `Cache-Control: no-cache, no-transform` stops both Next's
    built-in compression and Caddy's `encode` from buffering. Heartbeat
    every 15 s.
  - One idempotent cleanup runs from `cancel()`, from `req.signal` abort,
    and when a heartbeat `enqueue` fails.
  - Presence is the distinct member user ids in the subscriber set. Anonymous
    readers count as a number only. No separate presence map.
- `lib/study-live.ts`, one stream per study per tab:
  - **Remote op:**
    - `v ≤ local`: drop it
    - `v = local + 1`: apply it
    - otherwise: refetch the chapter
  - **Own ack:** if `v > confirmed + 1`, someone got in between → refetch.
  - **Ops in flight:** a remote op arriving meanwhile means refetch once
    they settle (pending comment text counts as in flight and is flushed
    first). If newer events arrived during the refetch, fetch again.
  - **After a refetch:** go back to the current path, or its nearest
    surviving ancestor. Newcomers landing on a stale `studies.position` use
    the same helper.
- Sync: when a contributor with sync on navigates, it is POSTed (300 ms
  debounce) to `studies.position`. Synced members follow, and newcomers land
  there.
- Connections: Caddy serves HTTP/2, so the browser's 6-connection limit only
  applies to `pnpm dev` on plain :3000. That's accepted.
- Tests:
  - Vitest:
    - concurrent ops serialize, with no lost update and publishes in
      version order
    - `setNags` from two users converges
    - a viewer can't apply ops
    - an invited-but-not-accepted user has no access
    - a removed member gets a 404
    - a deletion-test seeder for `study_members`
    - a deleted author's comment shows as "Deleted user"
  - Playwright, with two contexts: invite → accept → live edits → sync →
    the viewer is read-only (exit scenario 9), plus one reconnect after a
    forced stream close
- Manual: two browsers through Caddy at `https://localhost`.
